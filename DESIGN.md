# Technical Design — Circle Recommendations

**Goal.** Return ranked, joinable Circles for any seeded user, with a short and truthful explanation of each recommendation. Favor relevance and meaningful participation over popularity alone.

**Architecture.** FastAPI exposes `GET /api/v1/users/{user_id}/recommendations?limit=10`. The recommendation service uses SQLAlchemy to retrieve the normalized SQLite snapshot, apply eligibility filters, calculate relevance scores, and rerank candidates for diversity. The seed script loads five JSON sources idempotently and verifies referential consistency. Tables: `users`, `topics`, `user_interests`, `circles`, `circle_tags`, `memberships`, `activity`. Composite membership and interest primary keys prevent duplicate relationships. Additional indexes are defined for topic lookups, Circle discovery, reverse membership lookups, and time-based activity queries. In the current implementation, the service loads the Circle and Activity records it needs and performs much of the filtering and aggregation in Python; the indexes provide useful access paths for more selective queries as the dataset grows. Foreign keys protect relationships.

**Ranking.** First exclude joined, full, unlisted, and clearly dormant Circles (over 90 days without activity, or no recent posts and at most three chats). For users with stated interests, compute topic relevance from primary-topic matches (1.0) or tag matches (0.65); combine 70% topic relevance and 30% activity. Activity uses log-capped 30-day post volume (35%), chat volume (25%), recency (25%), and recent post engagement (15%). For no-interest users, rely on activity (70%), format/join accessibility (15%), and presence of descriptive metadata (15%). Next, greedily rerank using topic/tag similarity penalties and limit a primary topic to two placements. Stable Circle-ID tie-breaking makes results deterministic. Member-facing explanations are templates grounded in matched topics and available activity; no LLM calls.

**Tradeoffs.** Interpretable heuristics and simple all-Circle scoring fit 40 Circles and let reviewers reproduce outcomes. We have no actual recommendation labels or join feedback, so weights are hypotheses, not trained probabilities. No proximity claims are made because Circle meeting locations are absent. The synthetic snapshot is evaluated relative to its latest Circle activity timestamp; production should instead refresh rolling activity metrics using current time. A hard topic cap improves discovery but could suppress relevant options when inventory is thin. The fixed cold-start accessibility preference is a general heuristic, not a user-stated format preference.

**Validation.** Automated tests exercise all four planted scenarios (users 42, 7, 15, 23), enforce eligibility constraints across all 100 users, and verify HTTP errors and response structure. Real ranking quality would require online member feedback, joins, and engagement outcomes.

**Production path.** Move to PostgreSQL; store rolling activity aggregates and precompute candidate quality scores; add authentication/authorization, privacy review, migrations, observability, pagination, caching and scheduled recomputation. Introduce feedback-driven calibration and experimentation before adopting embeddings or learning-to-rank models. Ensure Circle join capacity is rechecked transactionally when a member actually joins.
